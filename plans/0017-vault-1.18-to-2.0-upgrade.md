# Plan 0017: Upgrade Vault 1.18.1 → 1.19 → 1.20 → 1.21 → 2.0 (standby pods first)

- Status: Draft, waiting for operator approval of the pod deletions
- Owner: operator (kmjayadeep), executed with the repository agent
- Related ADR: [ADR 0001](../adrs/0001-vault-external-secrets.md); TLS rollout in [plan 0012](0012-vault-internal-tls.md)

## Goal and scope

Move the three-node Raft cluster `vault/vault` from Vault 1.18.1 to the current 2.0.x, one minor at a time, with a snapshot before each step and standby pods upgraded before the active one. The chart is already at 0.34.1 and `server.image.tag` is pinned (PR #307), so each step is a one-line Renovate PR on `clusters/titania/apps/vault/helm-release.yaml` plus a controlled pod rollout.

Out of scope: `vault-agent-injector` (follows the chart), Vault configuration changes, auth/secret engine changes in `homelab-iac`.

## Starting state and prerequisites

Verified 2026-10-23:

- Chart 0.34.1, image `hashicorp/vault:1.18.1`, StatefulSet `updateStrategy: OnDelete`; pods `vault-0` (standby), `vault-1` (active), `vault-2` (standby), all `vault-version=1.18.1`.
- `disable_mlock = true` is rendered into the server config by the chart (required from 1.20.0 for integrated storage).
- Daily Raft snapshots to S3 via the `vault-backup` CronJob (verified today with the 2.2.1 CLI image); a fresh snapshot is cheap to take with a one-off Job before each step.
- Vault container `securityContext` has no `IPC_LOCK` capability. Vault images 1.20.11+, 1.21.6+ and 2.0.1+ require it (or `SKIP_SETCAP`), see "Important changes" below. The Renovate targets 1.20.4 and 1.21.4 are below those thresholds; 2.0.x is not, so step 4 needs the capability or env first.
- Open Renovate PRs: #324 (1.18.5), #325 (1.19.5), #346 (1.20.4), #347 (1.21.4); 2.x still awaits dashboard approval.

Important changes reviewed (HashiCorp LTS/change tracker): 1.19.0 LDAP upndomain DN-search hardening (LDAP auth not used); 1.20.0 `disable_mlock` required (already set), rekey cancellations use a nonce; 1.20.1 file audit devices cannot be executable (no file audit device here); 1.21.0 item-by-item list comparison for `allowed_parameters`/`denied_parameters` (review policies in `homelab-iac/vault-config` for list-valued params before step 3); 2.0.0 previously unauthenticated endpoints require auth, Vault rejects uncleaned paths, Azure auth precedence (not used).

**Approvals needed:** every step deletes Vault pods (`kubectl delete pod`), which AGENTS.md classes as destructive. One approval covering the procedure below for all steps, or one per step.

## Steps and gates

Per step (1.18.5 → 1.19.5 → 1.20.4 → 1.21.4 → 2.0.x):

1. Take a Raft snapshot: `kubectl -n vault create job --from=cronjob/vault-backup pre-<version>` and confirm the S3 upload in its logs.
2. Merge the Renovate PR; wait for the HelmRelease to be Ready. Because of `OnDelete`, nothing restarts yet; confirm `kubectl -n vault get sts vault -o jsonpath='{.spec.template.spec.containers[0].image}'` shows the new tag and the pods still run the old one.
3. Delete one standby pod (`vault-active=false`), wait for it to be Running, confirm it auto-unseals/joins (`vault status` shows `Sealed false`, `HA Mode standby`, the new `Version`). Repeat for the second standby.
4. Delete the active pod. A standby takes leadership within seconds; `vault.cosmos.cboxlab.com/v1/sys/health` returns 200 again, the old active comes back as standby on the new version.
5. Gate: all three pods `vault-version=<new>`, `vault operator raft autopilot state` healthy with three voters, the backup CronJob's next run (or a one-off) succeeds, `hashicorp/vault-action` JWT login in the homelab-docker-stacks deploy workflow still works, ESO SecretStores all Ready.

Before step 4 (2.0.x): add `IPC_LOCK` to `server.statefulSet.securityContext.container.capabilities.add` (or `SKIP_SETCAP: "true"` in `server.extraEnvironmentVars`) in the HelmRelease and roll the pods once on the current version.

## Validation and rollback

- `kubectl -n vault exec vault-1 -- vault status`, `kubectl -n vault get pods -L vault-active,vault-version`, `curl https://vault.cosmos.cboxlab.com/v1/sys/health`.
- Vault does not support downgrading a Raft data store. Rollback is restoring the pre-step snapshot onto the previous image (plan 0012 lists the restore drill as outstanding; do it before this plan if possible). Never run a restore without explicit approval.
