# LiteLLM model names

Use `qwen-intel` in LiteLLM clients that should follow the selected Intel Qwen variant without changing client configuration for each experiment. The Git-managed `router_settings.model_group_alias` maps it to `qwen3.6-27b-intel`, served as `qwen3.6-27b-intel-trial` by the internal `intel-vllm` service on port 8000. The versioned `qwen3.6-35b-a3b-intel` entry remains pointed at its original `intel-llama` backend; it is not a synonym for the 27B model and is unavailable while llama.cpp is stopped. Open WebUI connects through LiteLLM and selects `qwen-intel` by default for new chats (individual user defaults can take precedence). The direct `intel-llama` Ingress is not managed anymore; LiteLLM uses internal Kubernetes services.

The 27B entry advertises chat, reasoning, and function calling, with 65,536 input plus 16,384 output tokens within the running 80K vLLM context. One benign `tool_choice: auto` request directly to vLLM returned a structured tool call; test through LiteLLM and with varied workloads before relying on tool quality. The 35B entry retains its existing metadata and 128K limits, which apply only when its original llama.cpp backend is restored. No vision capability is advertised for either entry. Verify the alias and versioned names in the Model Hub after rollout.

Both the 35B and 27B entries use the same **internal accounting rates**, not actual costs charged by either local backend: $0.10/1M uncached input, $0.01/1M cache-read input, and $1.00/1M output. LiteLLM's custom pricing belongs in `model_info`. For OpenAI-style usage with `prompt_tokens_details.cached_tokens`, the intended charge is `(prompt_tokens - cached_tokens) * 0.0000001 + cached_tokens * 0.00000001 + completion_tokens * 0.000001`. Cache reads are counted only if the backend reports cached tokens and the installed LiteLLM version applies the cache rate; metadata or a Model Hub price alone cannot establish actual spend calculation. Verify a repeated benign request's usage and spend record (counts and cost only, no prompt text) after rollout. The 27B entry reuses these existing rates for consistent accounting; they are not a benchmark of operating cost.

To switch the stable alias to another variant, first configure a separate, running backend and LiteLLM `model_list` entry with the correct URL, exact served-model name, pricing (if known), and context limits. Then update only the `qwen-intel` mapping to point at that entry. Do not assume a versioned name remains an accurate pin if its shared backend is repointed. Prefer the Git-managed alias over editing Model Group Alias Settings in the Admin UI, which can create config drift. Verify alias visibility for client keys and a benign request after rollout; Kustomize validation alone cannot prove LiteLLM routing behavior. Changes here are GitOps desired state, not proof of a live rollout. The serving manifests now select the pinned Intel AutoRound cache and the vLLM Deployment as the sole B60 owner; the old GGUF PVCs and stopped llama.cpp Deployment remain for rollback. An earlier live-only trial and direct LiteLLM apply left the Intel serving and LiteLLM Flux Kustomizations suspended; committing manifests does not resume them or prove that Flux applied the revision. Check Git source revision, resource readiness, and routing before resuming each Kustomization. Never enable both GPU Deployments at once.
