# LiteLLM model names

Use `qwen-intel` in LiteLLM clients that should follow the selected Intel Qwen variant. Git maps it to the versioned `swift-qwen3.8-27b-q4ks-intel` entry, served by `intel-llama-swift-qwen38-trial` (Swift Q4_K_S GGUF + pinned F16 vision projector + MTP, 96K configured context, Q8 KV, MTP width 3, publisher sampling defaults). The database-backed Router Settings were aligned via authenticated `/config/update` after Helm rollout; `/router/settings` confirmed `qwen-intel` → `swift-qwen3.8-27b-q4ks-intel` and a benign alias request succeeded. Recheck effective routing after later changes; Helm values alone may not update it. The Tiel, Qwen3.8 AutoRound, older Qwen3.8 trial, Qwen3.6-27B vLLM, and Qwen3.6-35B llama.cpp Deployments are stopped with caches retained; their versioned LiteLLM entries cannot serve requests while stopped. Open WebUI selects `qwen-intel` by default for new chats (individual user defaults can take precedence). The old direct `intel-llama` Ingress is no longer managed; LiteLLM uses internal Kubernetes services.

Swift advertises chat, reasoning, vision, and function calling with 81,920 input plus 16,384 output tokens within its 96K configured window. One benign 32×32 red-square image request succeeded at 80K after the pinned projector was enabled; this is not broad vision-quality validation. A benign required-tool request at 80K and another after the 96K rollout returned structured `get_weather` calls through the versioned LiteLLM route (no tool was executed); varied multi-turn/tool reliability remains unverified. Up to ~25K text prompt tokens were benchmarked at the earlier 128K configuration, not at 96K with projector; near-limit memory safety and MTP speedup remain unverified. The stopped Tiel entry retains 80K metadata but cannot serve until restored. The stopped Qwen3.8 AutoRound entry retains its 80K metadata but cannot serve requests until that predictor is restored. The stopped Qwen3.6-27B entry advertises chat, reasoning, and function calling, with 65,536 input plus 16,384 output tokens within its configured 80K vLLM window. One benign `tool_choice: auto` request directly to vLLM returned a structured tool call; test through LiteLLM and with varied workloads before relying on tool quality. A single 125,931-token synthetic prompt completed at 128K configured context after the GitOps rollout; this is not a sustained-load or coding-quality guarantee. The Qwen3.8 trial advertises 114,688 input and 16,384 output tokens within its configured 128K window; tool calling is not advertised until evaluated. It reuses the existing internal accounting rates, not measured operating costs. Only Swift advertises vision; the other stopped Intel entries remain text-only in LiteLLM metadata. Verify the alias and versioned names in the Model Hub after rollout.

The Swift, Tiel, Qwen3.8 trial, 35B, and vLLM 27B entries use the same **internal accounting rates**, not actual costs charged by either local backend: $0.10/1M uncached input, $0.01/1M cache-read input, and $1.00/1M output. LiteLLM's custom pricing belongs in `model_info`. For OpenAI-style usage with `prompt_tokens_details.cached_tokens`, the intended charge is `(prompt_tokens - cached_tokens) * 0.0000001 + cached_tokens * 0.00000001 + completion_tokens * 0.000001`. Cache reads are counted only if the backend reports cached tokens and the installed LiteLLM version applies the cache rate; metadata or a Model Hub price alone cannot establish actual spend calculation. Verify a repeated benign request's usage and spend record (counts and cost only, no prompt text) after rollout. The 27B entry reuses these existing rates for consistent accounting; they are not a benchmark of operating cost.

To switch the stable alias to another variant, first configure a separate, running backend and LiteLLM `model_list` entry with the correct URL, exact served-model name, pricing (if known), and context limits. Then update only the `qwen-intel` mapping to point at that entry. Do not assume a versioned name remains an accurate pin if its shared backend is repointed. Prefer the Git-managed alias over editing Model Group Alias Settings in the Admin UI, which can create config drift. Verify alias visibility for client keys and a benign request after rollout; Kustomize validation alone cannot prove LiteLLM routing behavior. Changes here are GitOps desired state, not proof of a live rollout. The serving manifests retain the Intel AutoRound cache and the stopped 35B llama.cpp IQ3_S and IQ4_XS caches for rollback. Git declares `intel-llama-swift-qwen38-trial` as sole B60 owner; verify its readiness and versioned LiteLLM request before switching the alias. Verify the LiteLLM Flux revision and HelmRelease readiness after this change. With `STORE_MODEL_IN_DB=True`, LiteLLM's database-persisted Router Settings can override `router_settings.model_group_alias` from the HelmRelease: after a Helm upgrade to the restored Git alias, the effective alias still pointed to vLLM. It was corrected through authenticated `POST /config/update` with the complete alias map; verify `GET /router/settings`, `/model/info`, and a benign request after any future alias switch. Do not print auth credentials or other config values while checking. Check Git source revision and sole-GPU ownership before resuming each Kustomization. Never enable two B60 GPU inference Deployments at once.
